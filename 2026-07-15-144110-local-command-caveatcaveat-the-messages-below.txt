⏺ Agent "Analyze Fortran WENO schemes" finished · 7m 55s

⏺ Fortran analysis landed. Core findings:

  What the 27 is: 27 candidate least-squares sub-stencil reconstructions on the
  9-cell (two-ring) neighborhood. Each candidate = different precomputed
  pseudo-inverse (built at init by zeroing different stencil members, 27 SVDs
  per cell in mo_intp_coeffs_lsq_bln.f90). Loop body = 5 fixed dot-products +
  analytic Jiang–Shu smoothness + weighted accumulation with weight
  l_weights_s(is)/(β+ε)². No argmin, no sort, no data-dependent branching — the
  if (is.le.27) else-branch is dead code. Fixed trip counts everywhere (3, 9,
  27, 6). Per-timestep kernel is solve-free; SVDs only at init.

  gt4py verdict forming — portable, with reformulation:
  1. Fortran loops over cells and scatters to edges (upwind-ownership if). gt4py
  has no scatter → reformulate as edge-based gather via E2C + upwind rel-idx,
  exactly like existing compute_barycentric_backtrajectory_alt pattern.
  Smoothness is per-edge anyway (uses that edge's quadrature vector), so edge
  formulation is natural, kills the (6,3) per-cell working set.
  2. 27-candidate loop → Python-level loop launching per-candidate stencils,
  accumulating in Edge fields. No 27× unrolled monster stencil, no in-kernel for
  needed.
  3. Real work item: init-time coefficient setup port to numpy — 9-point stencil
  construction (create_stencil_c9), 27 candidate weight sets, 27 vectorized
  SVDs, l_weights_s, lsq_moments. icon4py already does linear LSQ pseudo-inverse
  via numpy SVD; extend that.
  4. WENO path uses quadratic reconstruction (6 moments,
  prep_gauss_quadrature_q); icon4py has the cubic quadrature stencil — quadratic
  variant needs porting (analogous).
  5. Caveat: only one live code path per routine (many stop "not implemented"
  branches) — port targets exactly that path. Branch is active research code.
